# 2026-08-02 AI 周挑战生成失败复盘

## 影响

目标周期从 `2026-08-03 00:00 Asia/Shanghai` 开始。冻结 audience 为 90 人，但最终任务数为 0，周期状态为 `FAILED`。管理员多次重试没有恢复。积分没有发放，也没有产生部分发布。

## 直接原因

基础设施和 DeepSeek 配置可用。8 次生成尝试中，最近 3 次都在固定 75 秒被 `AbortController` 中止并记录 `This operation was aborted`。此前影子运行已经出现 72 秒成功响应，说明 75 秒固定墙钟超时把“仍在持续返回的慢流”误判成挂死请求。

## 系统性原因

- 模型同时决定文案和数值业务规则，解析与业务校验面过大。
- AI 成功是整周发布的硬依赖；一个批次失败会使全部成员零任务。
- 批次为 25 人，单次输出大，尾延迟和非法输出概率上升。
- Worker 重启与人工重试没有可复用的批次检查点。
- 周日生成依赖进程内维护触发，缺少持久调度状态和业务健康告警。
- 健康接口只表达基础设施存活，没有区分“服务可用但当前周期缺失/降级”。

## 修复设计

1. 服务端确定基线、目标、三档奖励和所有整数积分；AI 只负责匿名文案，严格拒绝额外字段。
2. 批次缩小为 8 人。每批 AI 三次失败后使用已审核稳定模板，因此 AI 不再阻塞发布。
3. 成功批次按输入哈希落库，重启与重试复用检查点；最终任务仍在单一事务中完整替换并发布。
4. 超时拆为 180 秒总时限、60 秒首字节和 45 秒流空闲，SSE 进度刷新空闲计时。
5. BullMQ 持久调度器固定在周日 18:00 上海时区，维护巡检负责把缺失、失败和过期租约重新入队。
6. 周期记录 `AI/HYBRID/DETERMINISTIC` 和降级批次数；健康接口把基础设施 `ok` 与业务 `degraded` 分开。

## 验证与发布条件

- 自动化覆盖 300 人、纯 AI、完全降级、429/5xx/非法 JSON/超时、检查点复用、领取/冲正并发。
- staging 必须验证 390×844 与 1440×900 管理后台状态，验证 scheduler、队列、告警和 App/Worker 同版本。
- 付费影子连续两个周期必须为纯 `AI` 且零降级；否则不得作为开启生产开关的证据。
- 发布前备份并校验，先 migration 后同时更新 Web/Worker，观察至少一个调度窗口。

## 回滚与应急

若出现积分、重复发布或状态机异常，先通过受控 workflow 关闭 `WEEKLY_CHALLENGES`，保留周期、尝试、审计和数据库快照。应用可回退到同一已审查旧版本；新增 migration 不回退，数据库结构问题走前向修复。
