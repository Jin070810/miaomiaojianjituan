# 兑换订单状态转换

关联 #105。订单处理继续由管理员接口执行服务端 RBAC，状态、库存、实际积分退款、审计和通知处于同一事务。

| 操作 | 允许来源状态 | 结果 |
| --- | --- | --- |
| 确认 | PENDING | APPROVED |
| 发放/发货 | PENDING、APPROVED | FULFILLED；校验对应履约资料 |
| 更新物流 | FULFILLED 且原单号未被别人修改 | 保持 FULFILLED，仅更新单号 |
| 驳回 | PENDING、APPROVED | REJECTED；恢复库存及实际扣除积分 |
| 退款 | PENDING、APPROVED、FULFILLED | REFUNDED；恢复库存及实际扣除积分 |

每个转换都用数据库条件更新取得处理权，只有成功更新的事务能写该次审计、通知和退款。另一个请求先完成后，当前请求重新读取并核对最新状态，最多重试 4 次；不能把旧状态写回，也不能用旧状态生成错误的 beforeValue 审计。已完成或不再适用的转换返回当前订单。重复确认/发放不产生第二份审计；重复驳回/退款返回已有终态，库存和退款只处理一次。CLEARANCE_CANCELLED 不允许重新退款。

正常付费订单退款继续入账 REDEMPTION_REFUND。生日商品领取订单未扣积分：仅在已领取 GIFT、奖品归属/商品一致、quantity=1 且 unitCost=totalCost=0 时允许零价取消。取消仍恢复库存并写审计，审计 refunded=0、保留 birthdayPrizeId；不调用正积分入账函数，也不制造 0 积分退款流水。通知明确“未扣除积分”，原生日奖品保持 CLAIMED，不恢复年度抽奖或再次领奖机会。

普通零价或缺失有效生日奖品关系的订单不能伪装成赠品取消。批量历史订单维护仅选择 birthdayPrizeId 为空且单价/总价为正的订单，生日奖品须走单笔管理员流程，不随普通历史订单批量发放或退款。

无数据库 migration。并发回归覆盖确认/发放重复提交、退款与旧确认/发放竞争、驳回重试、生日零价取消和维护列表隔离。原实现已实际复现“退款完成后被旧请求覆盖为 FULFILLED”和重复确认审计；回退旧应用会恢复这些竞争条件，应优先前向修复。
