# v1.4 首周运营手册

本手册适用于首个正式周挑战和值守期。所有时间均为 `Asia/Shanghai`。任何异常优先保护积分与审计证据，不直接编辑生产数据库。

## 周日生成前

1. 记录当前线上完整 commit SHA，确认 `/api/health` 返回 200，`app.commit` 与 `workerVersion.commit` 完全一致。
2. 确认 `database=ok`、`redis=ok`、`worker=ok`，队列等待量未超过阈值。
3. 确认 `weeklyChallenges.enabled=true`、DeepSeek 配置完整，并执行一次受控模型连通验证。
4. 执行一次 SMTP 测试告警，确认值班收件人实际收到邮件。
5. 确认 02:15 本地备份和 SHA-256 校验成功，7 天轮转正常，发布免费快照 ID 已记录。
6. 确认 `WEEKLY_CHALLENGES` 开关变更只能通过审计化 workflow 执行。

## 生成后与周一

执行 `npm run ops:daily-check` 并保存 JSON。后台核对：

- `audienceCount` 等于当时有效普通成员数；任务数等于覆盖人数。
- 每名成员仅有一个任务；个人奖励均为整数且在既有规则范围内。
- 个人奖励理论总额不超过 10,000 分；竞速池保持 2,000 分。
- 最终失败批次为零；模型、prompt 版本、调用次数和 Token 统计完整。
- 周一 00:00 后周期状态为 `ACTIVE`，成员只能看到自己的任务。

## 每日巡检

1. 执行 `npm run ops:daily-check` 和 `npm run data:reconcile`。
2. 核对任务完成、领取、竞速赢家、撤销冲正和奖励重发记录。
3. 抽查积分流水与审计日志的 `requestId`、整数金额和余额变化。
4. 核对视频队列、Worker 心跳、订单处理和 SMTP 告警。
5. 核对最新本地备份、SHA-256 和本地 7 天保留清理；不要求或开通 OSS。

## 异常处置

1. 使用 `Weekly Challenge Production Switch` 将 `WEEKLY_CHALLENGES` 关闭，确认健康接口显示关闭。
2. 禁止手工补积分或删除失败记录；保留审计日志、工作流日志和数据库快照。
3. 如影响积分一致性，同时暂停视频提交、转账或兑换对应入口。
4. 运行只读对账，记录受影响成员、流水、周期和请求 ID，再决定前向修复。
5. 数据库 migration 不可逆时不得回退数据库；应用回滚前先核对版本兼容性。

## Issue #21 关闭条件

只有首周周期已激活、覆盖和预算证据完整、连续值守无未解决错账、恢复演练成功、发布记录完成后，才由人工审查者关闭 Issue #21。代码合并或一次健康检查不能单独作为关闭依据。
