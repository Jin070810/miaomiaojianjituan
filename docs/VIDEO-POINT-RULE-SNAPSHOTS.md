# 视频积分规则快照

## 口径与范围

实施假设：每条视频在**首次自动审核开始、调用外部抓取之前**锁定规则。该锁定时点尚待维护者在 PR 自审中明确确认；当前工作保留为 Draft，不代表已发布。

普通视频自动审核、人工仅处理申诉的已确认政策见相应政策 PR；本变更只负责各入口采用同一视频积分口径，需与 Worker 生命周期和自动审核政策变更一起集成验收。

| 情况 | 使用的规则 |
| --- | --- |
| 新提交第一次自动处理 | 此时完整读取的六项规则；还未处理时不提前锁定 |
| 抓取网络失败、队列重试、重启恢复 | 原快照，即使第一次抓取没有拿到数据 |
| 管理员重新抓取同一记录 | 原快照，抓取新的点赞等元数据但不换规则 |
| 自动驳回后的申诉 | 原快照计算默认积分，显式核定积分仍不能超过快照上限 |
| 驳回后以新记录重新提交 | 新记录首次处理时的规则 |
| 上线前已入账、没有快照的记录 | 保持到账和流水；历史规则标记未知，不补造当时版本 |
| 无快照的历史驳回记录通过申诉 | 事务内以当前规则捕获 `LEGACY_APPEAL`，明确不代表原审核规则 |

锁定包含最低点赞、固定档上限、固定档积分、除数、积分上限和投稿天数。生日加成独立留痕，不混入基础积分公式。

## 数据与事务

新增 `VideoPointRuleSnapshot`，以 `videoId` 为主键，与视频一对一。保存六项整数配置、`likes-v1` 公式版本、配置内容 SHA-256、捕获时间、来源配置更新时间和捕获来源。配置版本 A → B → A 时，内容 hash 相同；不同采用时点由时间字段区分。它不是发布顺序计数器，也不是密码学签名。

首次捕获使用短事务和按视频的 PostgreSQL advisory lock；快照与 `VIDEO_POINT_RULE_CAPTURED` 审计同事务写入。并发捕获只产生一份，外部抓取不占用该锁。并发修改全局规则时，捕获完整的旧配置或新配置，不混合字段。

数据库约束校验合法公式、来源、整数列及取值范围；触发器拒绝已存快照的更新，以及父视频仍存在时的删除。删除父视频/成员时允许级联清理。不依赖前端隐藏按钮保护历史依据。

`likes-v1` 保留独立计算器：低于最低赞数为 0，固定档采用固定积分，比例档 `floor(likes / divisor)` 后取封顶。未来公式升级必须增加版本并保留旧计算器，不能把所有旧快照转交新公式。读取时验证版本与配置 hash，未知或不一致时停止结算。

自动处理按快照重新计算权威分值，不依赖抓取适配器提供的 points。积分服务有快照时验证分值一致；通过、自动驳回和申诉审计记录规则、点赞、取整方式、公式结果、实际基础积分和两者是否不同。申诉显式核定分值继续记录操作人及复查说明，并受原快照上限限制。

兼容边界：原有内部 `creditVideoReward` 无快照调用仍保留可信输入，审计标记 `UNAVAILABLE`；这是兼容旧调用/测试的服务层入口，不是新增 HTTP 接口。当前正常抓取入口都会预先捕获快照。旧 Worker 不认识新规则，因此正式切换必须先排空旧 Worker，不能让不同版本同时处理视频。历史未知规则不会被当前规则伪装替换。

## 后台与只读复查

待处理申诉 API 返回可选 `pointRulePreview`，只读查询快照，不在 GET 建立快照。后台留空积分时显示锁定公式算出的基础积分；无历史快照明确显示金额尚未确定。生日加成注明如适用另计。核定金额可输入，但前端和事务都限制整数及该视频上限。

确认请求携带预览版本和默认计算金额；确认期间数据发生变化时拒绝旧确认，刷新后重新确认。旧客户端不带这些可选字段仍兼容，服务端结算始终执行快照规则及上限。申诉 API 取消硬编码的 5000 分上限，改由事务中的视频快照决定；输入外层上限仍为规则设置允许的 10,000,000。

申诉通过按 `photoId` 锁 → 视频行锁的顺序锁定，等待后重新读取申诉状态、视频状态和元数据。并发重新抓取先完成时，申诉拒绝覆盖 `PROCESSING`；同一申诉已完成时返回既有结果，不重复入账。

`npm run video:audit-approved` 使用每条记录的快照复查；没有快照的历史记录标记 `historical-rule-unavailable`。当前规则下的探测结果不等于历史错账，有快照的公式差异也需核对申诉和调整审计。脚本保持只读，同时按来源选择快手/抖音抓取器并关闭浏览器资源。线上抽样执行需计入平台请求预算，本次没有对生产批量抓取。

## 验证与发布

先复现三个失败：规则 50 → 80 后，旧视频申诉、网络重试、管理员重抓均错误改用 80。修复后针对性数据库测试覆盖这三项，以及并发唯一捕获、数据库不可改写、历史规则未知、申诉上限和显式调整、事务失败回滚、最低赞数/投稿天数、公式向下取整和过期确认拒绝。API 测试验证整数、权限、较高快照上限和事务失败传播。

Playwright 验收路径：管理员登录 → 视频与申诉 → 留空按锁定规则核定 → 显示实际基础积分 → 模拟确认期间数据变化被拒绝 → 刷新后入账；另覆盖历史未知规则、取消、空列表和驳回说明为空的禁用状态。使用生产构建、390×844 和 1440×900。Browser plugin not available，因此使用仓库 Playwright。

新增 migration `20261003192000_video_point_rule_snapshots` 只创建空的附属表及保护触发器，不扫描重写历史视频或流水。已在本地集成数据库执行，禁止修改该 migration；修正必须新增迁移。正式发布前仍需脱敏生产副本演练，记录外键创建锁等待、迁移时长、历史记录不变和旧代码兼容性。

Git attributes 固定 migration 文件以 LF 检出，避免 Windows `autocrlf` 改变新迁移的文件字节；本次没有修改任何已存在 migration 的 Git 内容。

应用回退不删除表或触发器，不回退历史积分。旧代码会读取最新规则，不能承诺继续履行已锁定口径；事故回退需暂停视频入账/申诉处理并排空旧 Worker，随后采用前向修复。未完成维护者自审、集成 staging 和生产副本演练前，不标记为已上线。
