# 自动审核、申诉与历史二审

关联 #105，依据维护者于 2026-10-03 确认的口径：普通视频自动审核，人工只处理成员申诉。

新视频由 Worker 按统一校验规则自动通过并入账，或自动驳回。不再创建 VideoSecondaryReview，不再按审核员人数分配任务；审核员提交自己的视频遵循相同自动流程。申诉仍由管理员处理，通过申诉、视频状态、积分入账及审计必须原子提交。

历史二审数据和审计记录保留，不批量改成通过或驳回，不删除待处理记录。原 PENDING 在界面显示为“历史未处理”，不代表当前待办。历史查询保留现有服务端权限：管理员可查全部，审核员只能查原分配给自己的记录，普通成员不可查询。

二审 POST 对有权限的旧客户端返回 410 / SECONDARY_REVIEW_RETIRED，无数据库或积分副作用；无权限仍返回 403。底层二审处理函数也明确拒绝，防止绕过路由继续调用旧逻辑。GET 附带 readOnly=true 和 policy=automatic-with-appeals，保持原列表字段兼容。

后台“视频与审核”默认打开申诉，只加载视频及申诉接口；历史二审按需进入独立只读页面。仪表盘 pendingVideos 仅包含待处理申诉；兼容字段 pendingSecondaryReviews 固定返回 0。审核员仍可使用其既有入团申请等职能。

管理员对已到账积分的纠错撤销保留，必须填写原因，在事务内撤销、补偿扣分及写审计。它不代替普通视频人工二审，且不重写历史二审结果；已发奖励和榜单的后续处理按独立撤销规则执行。

无数据库结构迁移或历史重写。发布时 Web 和 Worker 必须同时晋级同一批准版本，确认旧 Worker 已排空退出，避免旧进程继续创建已停用二审任务。回退旧版本会恢复二审流程，应优先前向修复。历史验收文档仅描述当时行为，以此约定及 AGENTS.md 为当前规则。

验收覆盖不创建二审、自审入口失效、所有旧二审写入无副作用、纠错撤销保留历史、申诉并发单次入账，以及桌面/手机历史查询、加载、失败、空数据和只读状态。CI/staging 与维护者自审通过前，不表示已上线。

容器 staging 在本机 HTTP 地址验收时显式设置 SESSION_COOKIE_SECURE=false，使浏览器和 Playwright API 请求使用一致的 Cookie 规则。Compose 默认仍为 true，正式 HTTPS 环境保持 Secure Cookie。
