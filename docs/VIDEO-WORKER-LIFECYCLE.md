# 视频 Worker 的重试、恢复与健康约定

关联工作项：#105。当前变更是 Worker 生命周期与故障告警修复，不包含审核政策和发布流水线的后续变更。

故障告警使用的 Nodemailer 锁定为 10.0.9，覆盖本次审计发现的生产依赖公告；Node.js 22 满足其运行要求。验证包括实际本地 SMTP 认证发送、收件人拒收和现有告警冷却/错误处理测试，未向外部收件人发送测试邮件。

一次业务提交最多执行 3 次抓取流程，首次开始后的处理预算为 10 分钟。快手抓取流程内部的 HTTP 重试不等于业务尝试次数。VideoProcessingState 保存累计次数、首次开始时间、下次可重试时间、租约与最后失败分类，Redis 丢失任务或 Worker 重启不会清零它们。

领取尝试时在短事务内锁定视频行，获取 120 秒租约并增加次数。网络抓取在事务外执行。写入抓取结果时再次验证租约；视频元数据、最终状态、积分、联动奖励及审计使用同一事务。过期的旧 Worker 不能覆盖新租约的结果或清除新租约。

瞬时抓取失败退避重试；确定性链接错误直接自动驳回。耗尽次数/总时间后终止，向成员区分抓取暂不可用与系统处理暂不可用，允许按已有规则重新提交或申诉。显式重新抓取才在审计事务中重置预算；重复请求不会反复重置。

恢复扫描按提交时间和 ID 分页，跨循环推进游标，绕过仍持有租约或未到重试时间的记录。队列中已经 failed 的任务会核对并终结业务状态，不会被删除后无限补发。已在 waiting/active/delayed 的任务不重复创建，返回的 enqueued 是实际新增数量。

Worker 健康由两种信号组成：

- Redis 心跳：每个实例独立 key，45 秒 TTL，保存 release SHA 和 running/draining 状态。Web 优先读取自身版本对应实例，旧实例退出只能删除自己拥有的心跳。升级兼容期仍写旧共享 key。
- 独立 Node supervisor：接收 Worker 的事件循环 IPC 心跳；运行时超过 60 秒没有心跳，先发送 SIGTERM，65 秒内不能退出则强制结束，父进程非零退出后由 Docker restart 策略恢复。Redis/数据库网络故障不会单凭心跳写入失败触发这个看门狗。Docker 的 unhealthy 标签本身不会自动重启容器。

启动后的业务维护不再阻塞定时心跳。正常关闭时停止领取/调度，等待队列和已开始维护任务，并在排空过程中继续写 draining 心跳；完成后清理自己拥有的心跳。Compose 的停止宽限为 75 秒，超出时仍可能被强制终止，重试与事务必须承受这个边界。

迁移与回滚：

- 新增 migration 20261003123000_video_processing_budget，仅创建附属表、约束与索引，不改旧 migration，不重写历史积分或视频。
- 历史处理中记录在首次领取尝试时建立预算。已耗尽的旧 failed 队列任务会被恢复流程终结。
- 老版本应用可以忽略新表，应用回退不需要删除它；回退到旧 Worker 会失去新重试保护，因此应优先前向修复，并在发布记录中明确临时保护措施。
- 发布前仍需脱敏生产副本 migration 演练、候选镜像 staging、自动发版验收和正式发布记录，不要求逐次人工自审。此文档不是上线证明。

验证覆盖：真实 BullMQ 的三次重试及 failed 恢复、数据库持久预算、并发租约、旧租约隔离、时间预算、显式重试幂等、元数据与积分原子提交、恢复扫描推进、实例心跳归属、维护/排空心跳和 supervisor 超时。实现参照 BullMQ 的延迟任务约定：moveToDelayed 使用当前锁 token，再抛 DelayedError，避免消耗业务重试预算。
参考：[BullMQ 延迟任务约定](https://docs.bullmq.io/patterns/process-step-jobs)。
